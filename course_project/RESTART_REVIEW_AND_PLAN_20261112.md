## 必须处理的问题

- **恢复路径**：重建当前目录的 editable 安装，检查脚本入口；隔离环境验收，不能只依赖临时 PYTHONPATH。
- **评分语义**：实际加载的 injection_task_0、1、3 使用 `value or "" in subject`。构造向攻击账户转账、备注仅为 `unrelated text` 的反例，三者仍返回攻击成功。原来的目标 7 不受这三处问题影响。主实验先选通过语义检查的目标；不悄悄修改原评分器。
- **正常任务语义**：实际加载的 user_task_5 要求支付涨价 10% 后的差额，但检查 50 元转账，与文字含义不一致。需要按预先声明的任务语义审查规则处理；任务范围在正式结果出现前确定。
- **日期缺失**：旧 task_0 的付款日期未提供，原系统提示要求不猜测，Agent 追问而未付款。不能为了提高基线临时替模型补参考日期。如加通用日期约定，必须作为所有条件共享、明确披露的运行设定，且单列原提示行为。
- **日志与完整性**：旧运行器是 pilot，缺少完整 wire request 快照、输入/工具/提示哈希、覆盖全部工件的清单、逐 episode 完成验证和可恢复调度；manifest 中仅 HEAD 不能证明当时无未提交修改。
- **记录路径**：旧 TraceLogger 按 pipeline/task/attack/goal 命名；trial 已隔离。正式执行必须同时隔离条件、trial、攻击配置和任务，并统一结果读取路径，防止缓存、覆盖和路径不一致。
- **预算与时段**：旧适配器没有低谷时段门禁，previous_spending 只累计 AgentDojo 本地日志，未合并 A-Mem 支出；正式运行必须合并项目账本、计入检查器和未知用量预留。
- **重复性**：`random.seed(trial)` 只影响本地随机过程，不是固定服务端 LLM 随机种子；温度为 0 也需要真实重复。比较条件使用相同冻结攻击文本及初始环境，记录独立调用。
- **攻击覆盖**：3 次修改密码失败不能说明其他攻击无效，也不能证明新增防御会有收益。开发阶段需检查注入是否被读取、目标本身是否可执行和其他固定公开攻击配置。

## 研究范围与主要问题

建议题目：银行工具调用 Agent 的执行前授权检查：基于 AgentDojo 的复现与安全—效用评估。

研究三个问题：原版 Agent 在正常/恶意外部数据下分别如何表现？现成防御的安全与任务完成权衡能否在替换模型的子集上观察到？增加一次写操作授权检查，怎样影响攻击成功、正常完成、误拦与成本？

论文复现目标对应原论文 Section 4.1、4.3 和 Figure 6、9 / Table 5 所研究的正常效用、攻击下效用与攻击成功率。不能把全任务、旧模型的原论文百分比当作本子集的同条件目标。运行行为复现、比较趋势一致或不一致、精确数值匹配须分开表述。

## 后续步骤与验收

### 1. 固定历史边界并修复环境（约 0.5–1 小时）

保留旧 commit、失败记录、六次轨迹及学习文档，建立新的恢复阶段目录和入口说明；修复 editable 路径；明确代码变更、实验记录和最终产物的位置。检查安装、导入、依赖和本地密钥配置是否可用，绝不输出密钥。

验收：当前目录直接执行离线命令成功；既有记录和 A-Mem 不被覆盖；新运行和旧开发记录分开。

### 2. 审查任务、工具和评分器，确定复现目标（约 1 小时）

检查 banking 的 16 个正常任务和拟用攻击目标的实际加载版本；用参考工具路径与正反例检查评分含义。给任务标注只读、合法写入、依赖外部参数等类型。按语义与运行条件确定纳入/排除规则，保留问题清单。保留原开发任务 0、1、2、3、13 的开发身份。

验收：有清楚的任务/目标清单、评分定义、论文对应关系；不根据后续攻击成功或防御效果选正式题目。

### 3. 小额开发试跑与继续开发决策（约 1–2 小时）

在开发任务上确认模型能执行正常任务、攻击文本确实被读取、攻击目标直接作为用户请求时的能力。优先检查原仓库公开模板及评分清楚的转账/定期付款变更/密码目标；记录所有尝试。开发数据可以用于设计和排错，不能混入正式主结果。

试跑测量实际调用时间和费用，决定实验规模。若没有攻击成功，先区分未暴露、能力不足和拒绝，不能为了制造结果关闭基本安全或按正式测试表现挑样本。若仍无适合测量防御的实验条件，停止新增防御路线，返回 A-Mem 后备或明确接受零成功率研究；后者不得包装为防御提升。

验收：工程、指标和可解释的基线行为成立，剩余时间能完成重复实验、分析与材料。判断不以修改是否有正收益为条件。

### 4. 实现一项主要修改并完成开发验收（约 2–3 小时）

推荐候选：每次有状态变更的工具调用实际执行前，检查操作及参数是否在用户授权范围内。输入包括原始任务、工具说明、拟执行参数和必要的已观察业务依据；外部数据仅提供业务事实，不能自行增加授权。检查器不访问 task ID 对应答案、攻击目标标签、参考工具序列、评分器或未读环境状态。

被拒绝的调用不执行，返回与 call ID 对齐的结构化工具结果，让 Agent 在相同总步数限制内继续。多工具请求按实际顺序逐个检查，不能先执行再拦截。只读工具不增加无用检查。检查器接口错误或格式损坏单列为技术失败，不计为防御成功。

原版、现成 repeat_user_prompt、原版加新检查器构成三个独立条件。新检查器不叠加现成防御，以隔离唯一主修改。前者是作者防御的复现参照，不能声称为我们的发明。

验收：正常授权写入可通过；额外改密码、篡改收款人、越权字段、多调用绕过等开发反例被正确处理；检查费用及决策理由可追踪。开发测试不替代真实实验效果。

### 5. 冻结正式协议与验收正式运行器（约 1 小时）

冻结任务、攻击目标/模板及 payload、三条件、模型、提示、参数、3 次重复、总步数、超时、技术重试、停止规则、费用和分析方案；记录源文件与数据哈希及干净的代码 commit。

建议基础规模：8 个通过语义审查的正式正常任务、2 个攻击目标、1 个固定公开模板、3 条件、3 次重复。正常 72 个 episode，攻击 144 个，合计 216 个，另列攻击目标能力检查。若审查后范围不同，按实际矩阵重算；第二模板属于预先决定的扩展，不能看正式结果后追加并混为原计划。

主指标：无攻击任务完成率、攻击条件任务完成率、攻击成功率、安全完成率（完成用户任务且攻击未成功）。技术失败、未运行和未暴露单列，主结果保留所有预定配对；暴露子集仅作诊断。均值/样本标准差按完整 trial 汇总，同一任务的多种攻击不视为独立用户任务。

正常动作误拦需要额外语义审阅，不能把正常 episode 完成率下降直接等同于误拦率。语义审阅标注审阅者及依据。

验收：先做正常、攻击、拒绝、异常、恢复和轨迹保存等离线/开发检查，确认完整结果可对账后才运行正式矩阵。

### 6. 正式重复实验（约 3–5 小时，以试跑速度为准）

按冻结列表、相同初始环境与攻击文本执行；条件顺序固定或预先平衡，记录时间。每个 episode 有独立目录和可恢复状态。所有 Agent 和检查器调用保留请求、回答、usage、耗时、拦截和工具状态变化；按官方空闲时段门禁启动每次调用。

保留全部正式结果。不因成绩差重新采样、不替换失败任务。技术恢复仅按预先规则进行并保留原失败尝试；实质协议修改必须留版本和原因，必要时重新建立可比基线。

新增阶段暂以 15 元为最高预算建议，正式开跑前按全部既有项目支出统一核算，仍受累计 100 元上限约束。上限不是预测费用或账户余额。

验收：预定矩阵完整，或未完成项清楚披露；账单估算及未知用量有边界；技术失败不被解释为安全收益。

### 7. 独立复算、机制诊断与解释验收（约 2–3 小时）

从 episode、轨迹和环境状态重算结果，回放所有可回放的正式记录，核对请求数和攻击 payload；区分回放验证与新模型重跑。

按预定类别检查：攻击成功、抵抗且完成任务、攻击失败但用户任务也失败、正常任务被误拦、同工具参数篡改、无有效暴露。定量描述收益/损失来自哪些任务，展示至少一个支持结果的案例和一个边界/失败案例。全零攻击结果只能支持本攻击集合未成功，不能证明普遍安全。

验收：每项主要结论能连到具体记录；没有用挑选案例代替总体结果；主要疑点在写最终结论前解决或明确界定。

### 8. 英文报告、PPT 与中文讲解稿（约 3–4 小时）

结果和解释验收后制作英文报告（不超过 10 页）和英文模板 PPT；正文与布局沿用报告黑白灰要求，PPT 保留蓝色模板，图文表可用色。中文讲解稿随最终幻灯片生成。优先使用流程图、工具行动链、实验矩阵、结果图与可追溯案例，避免长段落。

过程持续保留图表数据、日志摘录和可视化素材；最终材料不得把旧 pilot、合成反例或离线假 API 测试当成正式模型成绩。

验收：报告、图表、PPT 数字一致；你能解释复现目标、修改、指标、正负结果和限制；姓名学号最后填写。

### 9. 代码交付、录制和提交检查（约 2–3 小时）

整理可读提交、安装运行说明、正式配置、证据包及无需付费的复算入口，检查新目录恢复后的安装步骤和秘密排除。按你的决定处理学生 GitHub 发布，不能复用已拒绝的发布授权。你完成不超过 15 分钟 Zoom 录制，检查视频及仓库访问，再提交报告、GitHub 链接和展示链接。

验收：三项课程必需材料齐全、可访问；录屏是实际完成的视频，不以 PPT 或讲稿代替。

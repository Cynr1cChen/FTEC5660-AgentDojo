# 项目执行框架

## 暂定研究题目

**银行业务 Agent 的行动一致性检查：基于 AgentDojo 的提示注入复现与防御分析。**

题目中的具体防御在基线试跑后锁定。首轮不同时实现多种新防御。

## 1. 选题和复现目标

已确定 AgentDojo，使用其中的多步工具调用 Agent 与模拟 banking 任务。目标是复现“工具返回的外部内容可改变 Agent 行为”这一已报告能力／风险，并量化有无攻击时的表现。保留基线成功和失败，不预设 DeepSeek 一定遭受攻击。

模型替换、benchmark 修订、接口适配、缺陷修复均写入环境记录。原论文数字作为有条件的参照；不把不同模型／不同版本上的差异归因为新防御。

## 2. 环境与开发试跑（进行中）

- 获取官方仓库，固定上游提交和 benchmark。
- 建立独立 Python 环境，保存依赖版本。
- 验证参考工具执行、评分器和攻击生成。
- 接入 DeepSeek，记录模型、生成参数、token 和错误。
- 在预先指定的 3 个用户任务、2 个攻击目标上试跑，无 API 时只运行离线验证。

验收：真实轨迹可回放检查；正常任务有可理解的完成／失败原因；攻击已通过实际工具输出进入模型上下文；费用可估算。

## 3. 锁定正式实验

- 将首轮任务标为开发用途。剩余 banking 任务作为正式测试候选，先检查合法性和适用范围。
- 根据观察确定范围是否足够；若任务过少，明确报告小样本限制，或有理由地增加另一个场景。
- 固定攻击模板／目标、任务列表、参数及 3–5 次重复试验目录。
- 不根据测试答案选择防御阈值，不只保留成功任务或成功攻击。
- 固定一项现成防御作为参照，例如 `repeat_user_prompt`，并与无防御基线共用模型和参数。

验收：正式测试列表、指标与比较条件已写入配置，不在看结果后随意更换。

## 4. 实现一个主要修改

候选是在有外部影响的工具执行前检查“工具名称＋参数”与原始用户任务的一致性。检查器只能使用真实运行时可获得的信息，不访问任务评分器、参考答案或攻击者目标。

明确哪些操作接受检查、哪些证据可用、拒绝后如何返回错误并让 Agent 继续，以及额外模型调用成本。合法付款常需从账单读取金额和收款人，不能把“来自文件”直接当成越权。检查器本身也可能受不可信内容影响，应保留失败案例。

验收：无防御、现成防御、修改版之间只有已记录的防御机制差异；兼容性修复对所有条件相同。

## 5. 评测与分析

- 正常任务完成率。
- 攻击条件下的任务完成率、攻击成功率，以及任务完成且攻击失败的联合比例。
- 正常任务误拦截、额外请求量、token、耗时和费用。
- 攻击目标直接作为合法用户请求的能力检查，识别“模型本来就不会做”的混淆。
- 标记基础设施错误和缺失结果；不给这些 episode 贴上安全成功标签。
- 重复试验报告均值与方差；按用户任务分组分析，注意同一任务的不同攻击样本不独立。
- 分类案例：合法任务失败、被诱导行动、成功抵抗且完成任务、阻断攻击但任务也失败。

验收：每项图表能追溯到原始 episode 和配置，结论不超出样本范围。
